# Feature: Internationalization (i18n)

- **Status:** done
- **Phase:** cross-cutting (web)
- **Size:** L
- **Surfaces:** web
- **Links:** ADR 0005 (frontend stack), `.ai/conventions.md` (TypeScript + Presentation rules), `.kilo/skills/workpulse-ui/SKILL.md` (copy rules)

## Problem

`apps/web` ships English copy hardcoded across routes, feature components,
validation schemas, status labels and error mappers. The product cannot be used
by Vietnamese-speaking staff and every new string is unreviewable. One catalog
per locale, resolved per request, gives the UI a single copy source, makes the
language switchable without reloading a route, and stops wire values or API
codes from leaking into the interface.

## Business rules

- Supported locales are **English (`en`, default)** and **Vietnamese (`vi`)**.
- The active locale is stored in the `wp_locale` cookie (`SameSite=Lax`, path
  `/`, one year). URLs are not prefixed; routes stay locale-agnostic.
- An unknown or missing cookie resolves to `en`. The cookie is validated
  server-side; only known locales are persisted.
- The language switcher is available on every authenticated screen (header),
  plus the login/home surfaces, and applies immediately without a page reload
  of the current route (server action + `router.refresh()`).
- Server Components use `next-intl/server` (`getTranslations`,
  `getFormatter`); Client Components use `useTranslations`, `useFormatter`,
  `useLocale`.
- Every user-visible string, `aria-label`, placeholder, validation message,
  toast, empty/error state and metadata title/description comes from a catalog
  under `apps/web/messages/<locale>/`. No user-facing literal remains in
  components, schemas or feature helpers.
- Message keys are namespaced by surface (`common`, `nav`, `auth`, `home`,
  `dashboard`, `<feature>`). Feature catalogs mirror `features/<name>/`.
- Interpolation uses ICU message syntax. Count copy uses ICU plurals; the app
  never concatenates a count with a noun in code.
- API errors stay code-driven: stable `ApiError.code` values map to catalog
  keys. Raw codes and raw server text never reach the DOM.
- Dates, times, numbers and money are rendered with the active locale through
  `Intl`/`next-intl` (`useFormatter` or explicit locale). Month names must not
  come from a fixed English `dayjs` format.
- Server-rendered `<html lang>` reflects the active locale; metadata is
  generated per request.
- Missing keys fail loudly in development and fall back to English in
  production; a guard test asserts both catalogs expose the same key set.
- The test suite renders with the English catalog through a Vitest alias, so
  existing English copy assertions keep proving the real messages.

## Scope

- `next-intl` integration in `apps/web` (request config, provider, typed
  messages, locale cookie, server action, switcher).
- `en` + `vi` catalogs for every current `apps/web` surface.
- Migration of all user-facing copy in `app/`, `components/`, `features/` and
  `lib/` (including labels, error mappers, zod messages and empty states).
- Locale-aware date/time/number/money formatting.
- Localized page metadata (titles/descriptions).
- Test infrastructure: `next-intl` mock alias, catalog parity test, switcher
  test, and an updated copy assertion where the English output changes.
- Docs: this spec, `.ai/features/README.md`, `apps/web/AGENTS.md`,
  `.ai/conventions.md`, `tasks/TODO.md`.

## Out of scope

- API-side localization, localized API error messages or translated event
  payloads. The API remains English-only; the web maps stable codes.
- URL-prefixed locales (`/en/...`, `/vi/...`), locale-specific SEO/`hreflang`
  or per-tenant default languages.
- Persisting the locale on the user account (requires an API change).
- Right-to-left layouts and additional locales.
- Translating stored user data (employee names, notes, department names).

## Decisions (PO, 2026-10-26)

1. **Locales:** English + Vietnamese, English default.
2. **Scope:** full translation of `apps/web`, not only infrastructure.
3. **Resolution:** cookie (`wp_locale`), no URL prefix; the existing auth
   `proxy.ts` stays untouched.
4. **Implementation:** `next-intl` v4 (typed messages, ICU, formatter hooks,
   App Router support; adds one runtime dependency, justified here).
5. **Catalog layout:** one JSON file per surface per locale, merged in
   `messages/index.ts`; `features/<name>` owns its namespace.
6. **Test strategy:** Vitest aliases `next-intl` to a mock that resolves the
   real English catalog through `use-intl` (declared as a devDependency because
   the mock imports it directly), so component tests exercise real copy without
   provider boilerplate.

## Edge cases

- Missing/unknown `wp_locale` cookie → English; `<html lang="en">`.
- A user switches language while a query/mutation is pending: copy switches,
  in-flight data is untouched; the switcher disables while pending.
- A translated string contains `{` braces or apostrophes → ICU escaping is
  verified for the two catalogs.
- Long Vietnamese labels in the header/dialogs/tables must wrap or truncate
  without breaking the 390px layout; the switcher keeps a 44px touch target.
- A missing Vietnamese key falls back to English without crashing a page.
- Catalog parity: `en` and `vi` must expose identical keys; a test fails the
  gate otherwise.
- Locale-aware month names: Vietnamese renders Vietnamese month labels, not
  English ones.
- API-server English `error.message` is only a last resort for unknown codes;
  known codes always use the catalog.
- Server Components and Client Components resolve the same locale within one
  request (no hydration mismatch); the root layout passes locale + messages
  explicitly to `NextIntlClientProvider`.

## Acceptance criteria

- [x] Infra: given a request without `wp_locale`, when a page renders, then
      `getLocale()` returns `en` and `<html lang="en">`.
- [x] Infra: given `wp_locale=vi`, when a page renders, then server text is
      Vietnamese and `<html lang="vi">`.
- [x] Infra: given an unsupported cookie value, when a page renders, then it
      falls back to English (no 500).
- [x] Switcher: given the dashboard, when the user selects “Tiếng Việt”, then
      the cookie is set, the route refreshes and navigation copy is Vietnamese.
- [x] Switcher (failure): given an invalid locale submitted to the server
      action, then nothing is persisted and the current locale stays active.
- [x] Content: no user-facing literal remains in migrated components, schemas
      or helpers (catalog-only copy; verified by review + grep for known
      strings).
- [x] Formatting: given a date/amount, when locale is `vi`, then month names,
      separators and currency follow `vi-VN` conventions.
- [x] Errors: given a known API code, when a mutation fails, then the catalog
      sentence renders and the raw code never reaches the DOM.
- [x] Metadata: given `wp_locale=vi`, when `/login` or `/dashboard` renders,
      then the page title is Vietnamese.
- [x] Tests: every existing Vitest suite passes against the English catalog;
      a new parity test fails if a key is missing in either catalog; a switcher
      test proves the server action call.
- [x] Gates: `make check-web` green (typecheck + lint + Vitest).

## Outcome (2026-10-26)

`next-intl` v4 is wired through `i18n/request.ts` + `NextIntlClientProvider`;
the `wp_locale` cookie (validated server-side, English fallback) drives both
Server and Client Components, and the header/auth/home switcher refreshes the
current route. All app, shell and feature copy now resolves from
`messages/en/**` + `messages/vi/**`; payroll/report/attendance/leave/overtime/
recruitment date, number and money formatting takes the active locale. Page
metadata is generated per request.

Verification: `tsc --noEmit`, `eslint .` (0 warnings), `vitest run`
(54 files / 369 tests), and `next build` all green. The new catalog parity,
switcher and server-action tests live under `tests/i18n/`.
